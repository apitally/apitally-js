# Design & Plan Review - Apitally JS SDK v1

Critical pre-implementation review of `v1/design-js.md` and `v1/plan.md`, with `v1/design.md` and `v1/spec.md` treated as reviewable inputs, not fixed authority. Produced from four independent review lenses (OTel JS mechanics, core design coherence, plan structure, Node ecosystem/packaging) plus first-hand verification of load-bearing claims against the installed dependencies (express 5.2.1/router 2.2.0, hono 4.11.4, pino 10.2.0, @opentelemetry/sdk-trace-base 2.4.0 and 2.9.0, @opentelemetry/api 1.9.0, @opentelemetry/instrumentation-undici 0.19.0, @opentelemetry/resources 2.9.0).

Findings are numbered for reference and ordered by weight: verified factual errors first, then design under-specification and over-complexity, then plan issues. A verification pass was run over the raw findings list; what was checked and what was cut is recorded at the end.

## A. Verified factual errors in design claims

**1. The "public `resource` property" does not exist in OTel JS 2.x - and essentially all of the §2 user-provider introspection rides private internals (design-js §2, D1).**
The doc says the existing provider's resource "is read through its public `resource` property". Verified at sdk-trace-base 2.4.0 and 2.9.0: `BasicTracerProvider`/`NodeTracerProvider` expose only `_resource`; there is no public accessor. It does not stop there: the span processor list (`_activeSpanProcessor._spanProcessors`), the sampler (on the tracer's private `_sampler`; the provider no longer even has `_config` in 2.9), and the span limits (tracer's private `_spanLimits` - there is no public `getSpanLimits()` in 2.9.0, so the design.md §2 attribute-limit inspection on adopted providers has no public path at all) are all private. D1 is presented as the single internals-ride with defensive shape checks; in reality the entire user-provider path (attach, env resolution, sampler warning, limit warning) depends on four separate pieces of undocumented state. Two asks: (a) consolidate every private read into one version-gated internals adapter with explicit per-version shape tests, and document the full list instead of mislabeling one as public; (b) spike 1 must verify the mutation actually takes effect end to end (a span reaches Apitally's processor at runtime, including on `NodeSDK`-constructed providers) - a recognized-but-inert mutation currently fails silently with zero telemetry, the worst outcome per the SDK's own §12 posture.

> **Resolved (2026-07-21):** Confirmed by independent re-verification, and slightly worse than stated: `Tracer.getSpanLimits()` was public at 2.4.0 and removed by 2.9.0, and 2.9.0 turned `sdk-trace-base` into a shim over a new `@opentelemetry/sdk-trace` package with the provider class renamed — the internals restructure mid-2.x is a demonstrated fact, not a risk. Decision: resolved via finding 2 — the internals ride is deleted entirely, so no adapter or extended spike is needed. **Status: incorporated** (design-js §2/D1/spikes; plan U2/U6/KTD6/Risks).

**2. Worth asking whether D1's auto-attach machinery should exist at all (design-js §2, D1).**
Given finding 1, the alternative is: never touch internals; on detecting a user provider, warn once with the actionable fix (add the root-exported `ApitallySpanProcessor` to the provider's `spanProcessors` constructor array - the supported public path in OTel 2.x) and serve untelemetered on Apitally's side until then. Users with existing OTel setups are by definition sophisticated enough to add one constructor argument. The auto-attach saves that one line at the cost of a per-minor shape-check ladder across a pinned 2.x range plus a Renovate-gated drift watch. The doc never weighs "auto-attach internals" against "instruct-only"; it only designs the fallback for the shape-check failure. A senior reviewer would at least want the trade-off argued explicitly - or an upstream ask filed for a supported append path (OTel JS has been responsive to distro use cases).

> **Resolved (2026-07-21):** Decision: D1 goes instruct-only. The SDK never touches provider internals; on detecting a user provider it warns once with the `spanProcessors` fix while the adapters keep adopting (metrics and log capture flow without attachment — the degraded mode is partial, not total). The §2 introspection reads are replaced with public mechanisms: env from `OTEL_RESOURCE_ATTRIBUTES` at activation (a differing first-span resource warns once, activation value stands), sampler warning via runtime non-recording detection in the adoption path, attribute-limit warning dropped (payload isolation keeps captures off live spans, so it was largely moot). Spike 1 removed (number retained). Upstream issue for a supported processor-append path to be filed. **Status: incorporated** (design-js §2/§13/D1 row/spike 1; plan U2/U6/U13 sampler scenario/KTD6/Risks).

**3. `instrumentation-undici` does not respect `suppressTracing` - spike 6's premise is wrong (design-js §10, §13 D6).**
The doc claims the undici instrumentation "respects `suppressTracing`", so export traffic is invisible to instrumentations. Verified in 0.19.0 source (and unchanged on contrib main): the request-created hook checks `config.enabled`, CONNECT method, and `ignoreRequestHook` - never `isTracingSuppressed`. Consequences: every export POST via global fetch creates a CLIENT span and injects `traceparent` into Apitally's own export requests. On the SDK-owned-provider path those spans die at the in-flight-map miss (harmless overhead, but the doc's stated mechanism is simply not what happens); on adopted setups where the user runs their own undici instrumentation (included in `getNodeAutoInstrumentations`), Apitally's export traffic leaks spans into the user's backend every cycle. Fixes: pass an `ignoreRequestHook` matching the OTLP endpoint when the SDK enables the instrumentation itself, and either document or solve the adopted-setup leak. Correct the spike description before U2 runs it.

> **Resolved (2026-07-21):** Confirmed — zero `suppressTracing` references in the 0.19.0 build. Decision: keep `suppressTracing` on export cycles (well-behaved instrumentations honor it), add an `ignoreRequestHook` matching the Apitally endpoint on the SDK-enabled undici instance, document the adopted-setup leak (user-run undici instrumentation spans our export POSTs into their exporters), and file the upstream fix. Spike 6 re-premised on verifying the hook + proxy dispatcher. **Status: incorporated** (design-js §10/§13 D6/spike 6; plan U2).

**4. The Express route reconstruction port is broken for Express >= 5.2 - the plan's "v0 already handles both" claim is false (design-js §8; plan U13, Risks).**
Verified against the repo's own node_modules: express 5.2.1 uses the extracted `router@2.2.0`, whose `Layer` never stores `.path` or `.regexp` (matchers are closures). The v0 code being ported (`src/express/utils.js`, base-path reconstruction off `stackItem.path`/`stackItem.regexp`) cannot recover mount prefixes on Express >= 5.2. Separately, inline regex params (`:id(\d+)`) now throw at route registration on Express 5 (path-to-regexp v8), so the ported regex-param handling is Express-4-only. v0's CI pins `express@5.1`, which is why this was never caught; the plan's Risks section repeats the stale assumption ("route logic ported from v0 already handles both"). This changes U13's scope: route reconstruction for 5.2 is new code (e.g. probing `layer.matchers` and rebuilding templates from matched params), the U16 matrix must pin latest `^5` rather than a 5.1 floor, and KTD5 ("port over rewrite") needs re-scoping for this module.

> **Resolved (2026-07-21):** Verified, with corrections: the break is not ">= 5.2" — router 2.0 already uses closure-only matchers, so v0's `regexp`/`keys` branches were dead on all of Express 5; v0 appeared to work by reading mutable post-dispatch layer state (racy). Research across dd-trace, New Relic, Elastic, and OTel `instrumentation-express` (which supports Express 5 since 0.49.0) shows the industry-unanimous mechanism is registration-time capture of `use()`/`route()` path arguments — post-hoc readback is impossible (pillarjs/router#122). Decision: v1 uses registration-time capture on both Express majors — `useApitally` patches the shared router prototype found from the app object (verified working on 4.22 and 5.2; no module hooks), assembly semantics modeled on `instrumentation-express`. Setup contract: `useApitally` before any route registration, documented loudly; violations export a cleared route + once-warn naming the fix. Won't-fix: no early-register entry point, no retroactive readback on either major — v0's response-time reconstruction is not ported. **Status: incorporated** (design-js §8/§9; plan U13 files/approach/scenarios, Risks).

**5. Hono passive body capture has real fidelity and failure-mode gaps the doc does not mention (design-js §7).**
Verified in hono 4.11.4 `request.js`: (a) when the handler consumed the body directly off `c.req.raw`, `c.req.arrayBuffer()` returns a rejected promise - and `#cachedBody` caches that rejected promise, poisoning any later app-side body read; the SDK's completion-time capture must catch this and must never write to `bodyCache` on failure; (b) cache derivation is not byte-faithful: a handler that called `c.req.parseBody()` or consumed form data leaves a cache entry the derivation re-serializes (`new Response(body)`), yielding re-encoded multipart with a new boundary or worse - not the wire bytes, and inconsistent with the recorded content-type; (c) the doc's own guard contradicts itself: `c.req.raw.bodyUsed` is also true in the raw-consumption case the doc says is "not captured", so the documented outcome relies on an unspecified rejection-handling path - in a doc whose §12 rightly demands rejection handling on every SDK promise chain. Specify the actual guard (inspect the cache, not `bodyUsed`), the captured-byte semantics per consumption style, and the failure behavior, and pin them with tests.

> **Resolved (2026-07-21):** Confirmed, plus one refinement: the derivation branch of `#cachedBody` does NOT write to the cache — only the empty-cache branch does (caching whatever `raw[key]()` returns, including a rejected promise). Decision: the guard is cache inspection, not `bodyUsed` — the SDK reads the plain `c.req.bodyCache` field, captures only byte-faithful entries (`arrayBuffer`/`text`/`blob`; `json()` reads through `text`), skips `parsedBody`/`formData` (re-serialization fabricates wire bytes), never calls the request's body methods, never writes to the cache, and handles rejection on every awaited entry. Empty cache = no capture, so the poison path never fires. **Status: incorporated** (design-js §7; plan U14 approach + byte-faithful scenario).

**6. Wrapping Hono's `errorHandler` interacts badly with `route()` mounting and with `onError` call order (design-js §8; plan U14).**
Verified in hono 4.11.4 `hono-base.js`: `route()` decides how to mount a sub-app by identity-comparing the sub-app's `errorHandler` to the module-level default (`app.errorHandler === errorHandler`); a wrapped handler fails the identity check and changes the composition path for that sub-app's errors. This bites when the instrumented app (or an app the SDK wrapped) is itself mounted as a sub-app - modular-monolith Hono apps do this. Also: a user calling `app.onError(...)` after `useApitally` silently replaces the SDK's wrapper and kills exception capture with no warning. The design should state whether it wraps only non-default handlers (leaving the default-identity fast path intact), capture default-path exceptions another way, and document/enforce the `onError`-before-`useApitally` ordering.

> **Resolved (2026-07-21):** Confirmed (hono-base line 115 identity check; `onError` blindly replaces). Decision: the `errorHandler` wrap moves to first request — after `route()` mounting composition and after any user `onError` registered post-`useApitally`, resolving both interactions without special-casing. A handler replaced after the first request loses exception capture (accepted edge); "instrument the root app, not mounted sub-apps" is documented. **Status: incorporated** (design-js §8; plan U14 approach + onError scenario).

**7. `@opentelemetry/api` must be a peer dependency, not a regular dependency - global registration is exact-version-match for writes (design-js §2, §4, §16).**
Verified in api 1.9.0 (`internal/global-utils`): registering a global (tracer provider, context manager, propagator) is refused with only a diag error when the previously registered API copy's version string differs from the registering copy's - reads tolerate same-major, writes demand exact equality. The dependency policy (§16) makes `@opentelemetry/api` a regular `^1.9.0` dependency, so any second copy of the api package in the user's tree at a different version can make the SDK's context-manager/propagator/provider registration silently fail - and with it per-request context isolation and `suppressTracing`, the exact failure §2 says the registration exists to prevent. Every OTel instrumentation declares the api as a peer for precisely this reason. This one-line policy change also fixes the load-bearing weakness in the dual-build argument (§4): the "context holders already cross copies" claim only holds while both builds resolve the same api instance, which a peer dependency guarantees and a regular dependency does not.

> **Resolved (2026-07-21):** Confirmed (`registerGlobal` requires exact version equality for writes; reads tolerate same-major). Decision: `@opentelemetry/api` becomes a peerDependency (`^1.9.0`, devDependency for tests); design-js §16 records the rationale and §4's dual-build argument now cites the guaranteed single api instance. **Status: incorporated** (design-js §4/§16).

**8. "Register only when not already set" is not implementable as stated (design-js §2).**
The OTel API exposes no public getter for the current context manager or propagator (only the internal `context._getContextManager()`). Combined with finding 7's refusal semantics, the SDK cannot reliably know whether its registrations took effect. The workable contract is: attempt registration, then verify (a `context.with()` smoke probe), and warn once when context propagation is inert. The doc should say that instead of implying a clean conditional registration.

> **Resolved (2026-07-21):** Confirmed, with one refinement: `setGlobalContextManager`/`setGlobalPropagator` return a boolean, so a refused write is directly detectable. Decision: attempt registration (the API refuses duplicates and version mismatches, leaving user registrations untouched), then verify with a one-shot `context.with()` probe at activation — inert propagation warns once. With the finding-7 peer dependency, the version-skew refusal case largely disappears. **Status: incorporated** (design-js §2; plan U6 scenarios).

## B. Design: under-specified or more complicated than necessary

**9. D2 is the deferred-export mechanism renamed, plus a third state representation (design-js §6).**
The doc sells D2 as "uniform release model replaces deferred export", but for adopted spans the processor still holds an ended span until transport completion - that is deferral. On top of the buffer the reference already had, D2 adds the per-request record and the write-through helper, i.e. attribute state now lives in three places (live span, request record, export copy). Net complexity is arguably up, not down. That may still be the right call - but the doc should state honestly which invariants the record buys that buffer-plus-deferral did not, or the "one mechanism" claim will mislead maintainers. Relatedly, the accepted trade-off ("attributes that only reach the export copy are invisible to user-owned exporters on adopted spans") deserves one concrete example in the doc (final response size on a streamed response under `instrumentation-http`) so reviewers can judge how rare "rare" is.

> **Resolved (2026-07-21):** Confirmed — for adopted spans, holding the ended span until transport completion IS deferral; what D2 actually removes is the reference's commit/cancel handshake (`defer_export` at response start, cancel when completion precedes end) and the ad-hoc late-attribute merge. §6 now says so, states what the record buys (span-independent metrics and response-stage sampling — complete even when a user sampler made the adopted span non-recording — plus one accumulation point), names the three-copies cost plainly, and carries the concrete trade-off example (streamed response under user-run `instrumentation-http`: final size and corrected route reach only Apitally's copy). **Status: incorporated** (design-js §6 + D2 row).

**10. D2 leaves three hard questions unanswered (design-js §6-§7).**
(a) Late events, not just attributes: a `captureException` call or the Hono error-handler wrapper landing after an adopted span has ended must attach an `exception` span event to the export copy, and spec §6.4's "last exception event wins" makes event ordering matter - the doc only ever discusses attributes. (b) Merge semantics: "the export path applies the record onto the span copy it already builds for redaction, idempotently" never says who wins when the span already carries the same attribute (instrumentation-set `http.route` vs the record's final route) or what "idempotent" means for repeated releases. (c) Where the work runs: on the owned path, span end is triggered synchronously from inside the `res.end` patch, and release follows immediately - if export-copy construction, masking, and redaction (regex/JSON work over up to 50 KB bodies) run inline there, the "processed outside request handling" invariant (design.md §7) is violated in a single-threaded runtime with no export thread to hide in. Pin all three: enqueue-raw at release, build/mask/redact at batch-drain time, and define late-event and merge semantics.

> **Resolved (2026-07-21):** All three pinned, each matching the reference implementation. (a) Late events: no event mechanism needed — every SDK event write (Express error middleware, Hono `errorHandler` wrap, `captureException`) lands while the span still records on both paths (adopted spans end on `close`, after the SDK's `finish`-time work); a post-request `captureException` is dropped, as in the reference and stock OTel; spec §6.4 last-wins ordering is plain append order. (b) Merge: the exporter applies the record onto the export copy last — record wins over instrumentation-set values (the reference's `finish_export` merge, `{**span.attributes, **extra_attributes}`, has the same precedence); "idempotently" replaced with one-shot release semantics (exactly once per request, shutdown included — the reference's `held.pop`). (c) Where the work runs: release is an enqueue — record + stash ride a private span copy into the batch processor (the reference's `STASH_ATTRIBUTE` pattern); export-copy construction, record application, masking, and redaction run in the exporter at batch-drain time, satisfying design §7's "outside request handling" as timer-driven exporter turns. **Status: incorporated** (design-js §6/§7; plan U7 approach + scenarios).

**11. The pino patch works - but not the way the doc describes, and D4 has no spike (design-js §9, D4; plan U2).**
Verified against pino 10.2.0: each logger instance gets its own direct prototype; `writeSym` lives two levels up on a prototype shared by all instances of that pino copy (patching it covers pre-existing loggers, future loggers, and children - verified). So the mechanism is viable, but only via the shared grand-prototype; the doc's "the shared logger prototype's write method, resolved via `pino.symbols.writeSym` on a probe instance" glosses over a chain walk whose naive reading (patch the probe instance's direct prototype) covers nothing beyond the probe's own children. This chain shape is undocumented and may differ across pino majors. Three more D4 gaps: (a) none of the seven spikes covers the log patches, even though they ride the internals of three libraries - the same exposure class as D1, which does get a spike; (b) bundled/transpiled user code (esbuild/tsup/Next.js server bundles inlining winston or pino) and multi-copy installs escape a single peer-resolved patch entirely - unmentioned; (c) the stated limitation "custom transports in worker threads may evade the prototype patch" is imprecise - `writeSym` runs on the main thread before the transport handoff, so transport-using loggers are captured; what evades is loggers created inside worker threads and per-instance write overrides. Add a D4 spike across the supported winston/pino majors and fix the limitation text.

> **Resolved (2026-07-21):** Confirmed — the earlier prototype-chain experiment in this session matches the reviewer's: `writeSym`'s owner is a shared grand-prototype, and a direct-prototype patch covers nothing beyond the probe's children. Decisions: (a) new spike 8 verifies both patches (winston prototype, pino write-owner walk) across supported majors, and the verified majors become the declared peer floors; (b) §9 now describes the find-the-owner prototype walk (same mechanism family as §8's Express walk); (c) bundled/inlined copies (esbuild/tsup/Next.js server bundles) and multi-copy installs are documented as escaping the peer-resolved patch; (d) limitation text corrected — worker-thread transports are captured (`writeSym` runs on the main thread); what evades is loggers created inside worker threads and per-instance write overrides. **Status: incorporated** (design-js §9 + spike 8; plan KTD6/U2/U8).

**12. The internal diagnostics logger is console-backed while console is patched for capture - the feedback-prevention mechanism is never specified (design-js §9, §12).**
§12 defines the internal logger as "console-backed"; §9/D4 wraps console methods to capture application logs. The only thing preventing SDK diagnostics from being captured as request logs (or feeding back into the export path on export failures) is the "SDK/OTel self-log exclusion" - whose mechanism is never described for a capture point that sits on console itself. The structural fix is cheap: have the internal logger write to `process.stderr` directly, making exclusion unnecessary for the SDK's own output. As designed, an enrichment-failure debug log emitted inside a request context relies on an unspecified marker to avoid appearing in that request's customer-visible logs.

> **Resolved (2026-07-21):** Confirmed — the exclusion mechanism was unspecified for a capture point sitting on console itself. Decision: the structural fix as proposed — the internal logger writes directly to `process.stderr`, never through `console`, so self-capture and export-failure feedback are impossible with zero exclusion logic. The OTel half stays covered: diag is silent by default, the SDK never installs a console-backed diag logger, and the drop rule catches out-of-request records as a second layer. **Status: incorporated** (design-js §9/§12; plan U3).

**13. Apitally-first global registration can silently break a later user OTel setup - "documented ordering limitation" understates it (design-js §2; design.md §2).**
Because activation fires on the first request, the SDK registers its provider as the OTel global before any lazily-initialized user setup. When the user's `NodeSDK.start()` (or manual `register()`) runs later, the registration is refused with a diag error: the user's Datadog/Honeycomb pipeline gets nothing, and the SDK never knows. That is silent, total loss of the user's telemetry - a much worse failure than the phrase "ordering limitation" suggests, and it will be attributed to Apitally because Apitally works and their backend stopped. At minimum: name the failure mode explicitly in both docs and README, and log one visible line at activation when the SDK registers the global provider ("later OTel SDK setup will be ignored") - arguably worth an exception to the quiet-by-default posture given the blast radius.

> **Rejected (2026-07-21):** Won't-fix. OTel setup after the first request has been served is an anti-pattern (NodeSDK's own docs say init before app code) and not a realistic scenario to handle; `design.md` §2's "documented ordering limitation" stands as-is. No runtime signal, no doc changes. **Status: no changes.**

**14. Express shutdown has gaps on the stock production path (design-js §4).**
No signal handlers (correct), `close` listener on `req.socket.server`, `beforeExit` floor. But: (a) SIGTERM with the default handler terminates without `beforeExit` or `close`, so the stock Kubernetes shutdown path drains nothing unless the user wires `server.close()` themselves - this dependency must be documented loudly, not implied by "`shutdown()` is the documented path"; (b) the multi-server rule ("drains when the first one closes") never says what happens to the second server afterward - does it serve untelemetered, and does its telemetry get attributed correctly before the drain?; (c) `req.socket.server` can be absent or a dummy when `app.handle` is invoked directly (serverless-express style) - the close-listener attach needs a graceful no-op path. (One prior concern does not apply: since Node 19, `server.close()` also closes idle keep-alive connections, so on the >= 20.6 floor the close event fires promptly.)

> **Resolved (2026-07-21):** All three fixed. (a) design-js §4 now states plainly that nothing fires on a default-handled SIGTERM — the app must wire `server.close()` or await `shutdown()`, worst-case loss is the last export interval plus in-flights — and the U16 README rewrite carries a graceful-shutdown section. (b) Resolved by redefining the close-triggered drain as design.md §10 already defines it — a flush-and-send cycle, not teardown: the pipeline keeps running (timers unref'd), a dual-bound app keeps full telemetry on the still-open server, and another server's in-flight requests are never discarded; teardown belongs to `shutdown()` and the `beforeExit` floor. The close listener is tracked per distinct server. (c) The listener attach no-ops without a live server (serverless-style `app.handle` dispatch). New U13 scenarios pin the multi-server and no-server contracts. **Status: incorporated** (design-js §4; plan U13/U16).

**15. Per-request buffers have no global bound (design-js §6; design.md §6).**
1,000 spans and 1,000 log records per request, no cap on concurrent in-flight requests, no time-based eviction. SSE and long-polling endpoints (websockets are excluded; SSE is not) hold buffers - including stashed bodies - for the connection lifetime: hours x N connections x potentially MBs each. The buffers exist to make sampling and late attributes correct, but a global in-flight budget or a max-hold duration after which a request's buffers flush-or-drop deserves consideration before this ships. This is inherited from design.md; the JS doc repeats it without examining the memory model.

> **Resolved (2026-07-21):** Partially confirmed — the reference is less unbounded than stated: it carries a global payload-stash cap (`MAX_STASHED_REQUESTS = 2_048`, oldest evicted), which design-js had silently omitted; the biggest memory item (captured bodies) is therefore bounded. Decision: carry the reference's model explicitly — 2,048-request stash cap documented in §6 and pinned in U7; span/log buffers stay per-request-bounded only, with the SSE/long-poll hold-until-stream-end behavior stated plainly as reference parity. A global in-flight budget would be a cross-SDK `design.md` change, deliberately not introduced as a JS-only deviation. **Status: incorporated** (design-js §6; plan U7).

**16. The export worker's cycle can exceed its interval, and no non-overlap rule is stated (design-js §10).**
Worst case: 10 files x (10 s POST timeout + 0.1-0.5 s pause + one inline retry) is roughly 100-200 s for one cycle against a 15 s interval. The doc never says cycles are serialized (presumably they are, via the single timer chain), never says what happens when a cycle overruns, and never states the loss posture under sustained overload (spool caps evict; retention drops) - which is the honest answer and should be written down rather than left to the reader.

> **Resolved (2026-07-21):** Confirmed — none of it was stated. §10 now pins all three: cycles are serialized on one timer chain (next cycle armed only after the current completes, interval measured from cycle end), an overrunning cycle stretches the cadence instead of stacking, a mid-cycle flush request awaits the running cycle, and the sustained-overload loss posture is the spool's (oldest-first eviction metrics-last, 59-minute retention — bounded, oldest-first). U5 gains the no-double-send coalescing scenario. **Status: incorporated** (design-js §10; plan U5).

**17. Capture position relative to compression middleware is never pinned (design-js §7).**
Both `compression` (Express) and the SDK patch `res.write`/`res.end`; patch order decides whether the SDK sees application bytes or gzip bytes. The Hono tee at the `app.fetch` level always observes the post-compression stream. The doc mentions "gzip pass-through for pre-compressed response bodies" - which implies post-compression capture - but never states the rule per adapter, nor whether the 50,000-byte cap measures compressed or application bytes (they diverge wildly for compressible payloads), nor what the server does with a captured gzip body that was capped on compressed size. Pin capture position and cap semantics explicitly per adapter.

> **Resolved (2026-07-21):** Confirmed as under-specified, and the answer falls out of the wrap architecture: the Express `res.write`/`res.end` patches install in the `app.handle` wrap before the middleware stack runs, so compression's output feeds the SDK's patch, and the Hono tee wraps the returned Response after any compress middleware — both adapters observe wire bytes by construction. §7 now pins that rule, the cap/size semantics (wire bytes, agreeing with Content-Length so header short-circuit and running count never diverge), the bytes-path handling for compressed captures, and mask callbacks receiving wire bytes. U13/U14 gain compression scenarios. **Status: incorporated** (design-js §7; plan U13/U14).

**18. The Sentry trade-off is version-fragile vs package-fragile - spike 7 should enumerate packages, not just majors (design-js §14).**
`globalThis.__SENTRY__` is version-keyed internals but package-agnostic (`@sentry/node`, `@sentry/nextjs`, `@sentry/bun`, `@sentry/aws-serverless` all populate the same carrier); peer-resolved `import("@sentry/node")` is public API but misses every Sentry flavor except one. The doc frames the choice as "carrier walk vs public API"; the real question is which fragility you prefer, and for whom. Spike 7 should record `beforeSendEvent` availability per Sentry package and major, and the supported set should follow where the users are (Next.js is plausibly the largest).

> **Resolved (2026-07-21):** Accepted as a framing correction — the choice is package-fragile vs version-fragile, not internals vs public API. §14 now states the trade-off in those terms, and spike 7 enumerates client access and `beforeSendEvent` availability per Sentry package (`@sentry/node`, `@sentry/nextjs`, `@sentry/bun`, `@sentry/aws-serverless`) and major, with the supported set following where the users are. **Status: incorporated** (design-js §14 + spike 7; plan U2).

**19. The histogram downscale hides a resolution cliff, and spike 5 has no Plan B (design-js §11; plan U2).**
JS `sdk-metrics` exponential aggregation starts at up to scale 20 with no scale knob; the export path merges down to <= 3. That is up to 17 halvings of resolution discarded, making the JS histograms materially coarser than the Python reference's native scale 3 - "matching the reference implementation's `max_scale=3`" overstates the equivalence. If spike 5 (bucket-merge correctness) fails, §11's histogram design topples with no fallback, since ingest drops points outside [-2, 6] silently. Consider capping `maxSize` so the aggregator self-downscales earlier (shorter merge distance), and give spike 5 a pre-mortem fallback.

> **Rejected (2026-07-21):** The core claim is wrong: exponential buckets nest by powers of two, so merging high-scale data down to scale 3 is exact — the output equals what a native scale-3 aggregator records, i.e. the JS histograms are equivalent to the reference's `max_scale=3`, not "materially coarser". No Plan B is needed either: the downscale is ~30 lines of SDK-owned index arithmetic, not dependency behavior — spike 5 verifies our code against real aggregator output, and a failure is a bug fix.
