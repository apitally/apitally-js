# Apitally JS SDK Design

Language-specific design doc for the JavaScript/TypeScript v1 SDK, per the process in `design.md`. It maps each section of `design.md` onto the Node.js/Bun ecosystem and records every deviation as a conscious choice with rationale. The Python SDK (`apitally-py`) is the reference implementation; where this document is silent, the reference behavior and `design.md`/`spec.md` apply unchanged.

Deviations are numbered `D1`-`D8` for traceability and summarized at the end.

## 1. Product shape

Same package name (`apitally`), shipped as 1.0 with a clean break from 0.x. Alphas publish as `1.0.0-alpha.N` under the npm `next` dist-tag; `latest` stays on 0.x until GA.

Platform scope: Node.js >= 20.6 (declared in `engines`). The floor is inherited, not a syntax requirement: `@opentelemetry/*` declare engines `^18.19.0 || >=20.6.0` — the availability line of Node's `module.register()` customization-hooks API — and the SDK takes the >= 20 branch; it moves when OTel's floor moves. Node 20 is past EOL (April 2026) and stays in the supported range deliberately: an APM SDK's late adopters skew toward older runtimes, the Node 20 matrix lane proves the claim, and nothing in the design needs a 22+ feature — revisited when OTel raises its floor (SDK 3.0). Bun support is scoped to Hono, which is first-class (CI-covered on Bun); Express on Bun rides Bun's `node:http` compatibility layer — expected to work, untested, unclaimed. Known Bun gaps, documented: native fetch emits no `diagnostics_channel` events, so outbound HTTP produces no CLIENT spans on Bun (§13), and the proxy branch ships untested (§10). README and positioning say "Bun (Hono)", not "Bun". Edge and serverless runtimes (Cloudflare Workers, Lambda streaming) remain the domain of the separate `apitally-js-serverless` package.

The defaults table in `design.md` §1 applies verbatim, including the two 0.x behavior flips the migration guide must call out: `captureLogs` defaults on, `env` defaults to `prod`.

## 2. Integration with existing OpenTelemetry setups

Detection at activation uses the OTel API global: `trace.getTracerProvider()` returns a `ProxyTracerProvider`; a delegate that is absent or a `NoopTracerProvider` means no user setup exists. Never detect via `instanceof` — the user's provider may come from a different copy of the OTel packages (see §16).

**No existing tracer provider**: the SDK constructs its own `NodeTracerProvider` with an explicit always-on sampler and the resource from below, and registers it as the OTel global. `design.md` §2's "tracer provider only" scopes to signal providers (meter and logger providers stay private, below); the API globals that default to no-ops are also registered: `AsyncLocalStorageContextManager` as the global context manager (without it `context.with()` is inert — per-request contexts, the span handle, and `suppressTracing` all silently stop working) and the W3C trace-context propagator (user-registered outbound instrumentations inject through it). The API exposes no getter for current registrations, so the SDK attempts registration — the API refuses duplicates and version mismatches, returning `false` and leaving any pre-existing user registration untouched — then verifies the outcome with a one-shot `context.with()` probe at activation: inert context propagation (no manager won the registration) warns once. Span attribute value length limits are pinned to 65,536 on every constructor setting that could constrain them (`generalLimits` and `spanLimits`), so `OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT`-style env vars never clip the long regular attributes the pipeline reads (`url.full` feeds path/query derivation and redaction); capture payloads never sit on live spans (§7), so span limits cannot reach them.

**Existing tracer provider**: the user attaches `ApitallySpanProcessor` themselves. User-owned providers are supported from OTel JS SDK 2.0; 1.x is not supported (its span shapes predate the 2.0 renames and are rejected by the export pipeline — no detection or compat path). **D1 — instruct-only attachment**: OTel JS SDK 2.x removed `addSpanProcessor()`; processors are constructor-only, and every introspection alternative — the processor list, the provider's resource, the sampler, the span limits — is private state that OTel restructured across packages within the 2.x line (2.9 moved the provider into a new `@opentelemetry/sdk-trace` package and removed the last public read, `Tracer.getSpanLimits()`). The SDK never touches provider internals. On detecting a user provider it warns once naming the degraded mode and the fix: until `ApitallySpanProcessor` (public export from the package root) is added to the provider's `spanProcessors` constructor array (or the `NodeSDK` `spanProcessors` option), only metrics and the startup event reach Apitally. The adapters keep running — the middleware adopts the user's SERVER spans and the histograms are recorded in the transport layer, span-independent — but traces and request logs flow only through the attached processor: captured log records before attachment carry no request linkage (the in-flight map is processor-populated) and fall to the §9 drop rule, correctly, since spec §6.5 leaves request logs whose SERVER span never arrives unsurfaced. An upstream issue asking for a supported processor-append path is filed independently of 1.0. The processor's public contract makes user construction safe anywhere in their setup: the constructor takes no arguments and has no side effects (no config read, no I/O, no timers), and instances are thin shells forwarding every callback to the SDK's process-global pipeline (the §4 `globalThis` slot), so construction order relative to `useApitally` never matters. Callbacks arriving before activation find no pipeline and no in-flight map and fall to the §5 drop rule — in particular, the first request's SERVER span under user-run `instrumentation-http` starts before the wrapper has activated the SDK and loses that span while its metrics still record from the per-request record (the adapter's transport-completion call tolerates the map miss: metrics are recorded, everything else is discarded). `forceFlush()` and `shutdown()` called by the user's provider delegate to a flush of Apitally's downstream pipeline (releasing requests whose transport already completed) and never tear down the SDK — teardown belongs to the public `shutdown()`.

The `design.md` §2 introspection reads are replaced with public mechanisms. Env resolution runs once at activation, with one precedence algorithm per path. Own provider (design.md §3 precedence): `env` option > `APITALLY_ENV` > `OTEL_RESOURCE_ATTRIBUTES`' `deployment.environment.name` > `prod`. User provider (design.md §2: the provider's resource wins, and `OTEL_RESOURCE_ATTRIBUTES` is the only part of it readable at activation): `OTEL_RESOURCE_ATTRIBUTES`' `deployment.environment.name` > `env` option > `APITALLY_ENV` > `prod`, warning once when a differing non-default configured value loses. A programmatically-built user resource is invisible at activation; when the attached processor later sees a span whose resource carries a different `deployment.environment.name`, it warns once and the activation-resolved env stands — env never flips mid-process. **D8 — adopted-span export copies carry the resolved env.** Spec §5 requires `deployment.environment.name` to match the `Apitally-Env` header on every export, and design.md's "exported spans carry that provider's resource unchanged" assumed the provider's resource is readable at activation (it is in Python; it is private state in OTel JS 2.x). So the exporter rewrites exactly that one resource key to the activation-resolved env on Apitally's export copy when it differs — the user's span, resource, and exporters stay untouched, and every other resource attribute passes through unchanged. The sampler warning becomes runtime detection in the adoption path: a request arriving under an active but non-recording span context means the user's sampler dropped it, so the SDK warns once that only sampled traces reach Apitally while metrics stay complete (the per-request record is span-independent). The attribute-length-limit warning is dropped: there is no public read, and payload isolation (§7) keeps capture payloads off live spans, so user-configured limits cannot clip captured bodies — they can clip long regular attributes (e.g. `url.full`) on adopted spans, accepted.

Meter and logger providers are always private instances, never registered into OTel globals.

Resource construction follows `design.md` §2 with the concrete mechanism pinned: `defaultResource().merge(detectResources({ detectors: [envDetector] })).merge(resourceFromAttributes({ ...apitally keys }))` — the argument side wins each merge (verified at resources 2.9.0), so `OTEL_SERVICE_NAME`/`OTEL_RESOURCE_ATTRIBUTES` are honored (`defaultResource()` alone reads no env vars) and the Apitally-owned keys win last: `service.instance.id` (UUIDv4 per process), `deployment.environment.name` (the resolved env above), `telemetry.distro.name` = `apitally-js`, `telemetry.distro.version`. `envDetector` is fully synchronous (no promise-valued attributes — verified at 2.9.0), so activation stays synchronous (§4).

## 3. Configuration

Options are camelCase, mapped 1:1 from the shared option set: `writeToken`, `env`, `appVersion`, `disabled`, `captureLogs`, `captureRequestHeaders`, `captureRequestBody`, `captureResponseHeaders`, `captureResponseBody`, `maskQueryParams`, `maskHeaders`, `maskBodyFields`, `maskRequestBody`, `maskResponseBody`, `excludePaths`, `sampleRate`, `sampleOnRequest`, `sampleOnResponse`. The absent-vs-default distinction is TypeScript optionals: an omitted option is `undefined` and keeps env-var fallbacks in effect.

Env vars, precedence, re-call semantics, invalid-value handling, and the `APITALLY_DISABLED` activation-boundary recheck follow `design.md` §3 verbatim.

Semconv: the SDK's own SERVER spans emit stable HTTP semconv natively, so no opt-in mechanism is involved on the primary path. For user-owned instrumentations constructed after configure, `OTEL_SEMCONV_STABILITY_OPT_IN` is set to `http/dup` only when unset. Old-convention fallbacks are retained at every SDK read site (exclusion matching, query redaction, path derivation) for spans produced by user instrumentation that initialized with old names.

## 4. Lifecycle

**Configure** runs synchronously inside `useApitally()`: validate options, wrap the app (per-framework), compile patterns. No timers, no I/O.

**Activate** is gated in the SDK's outermost per-request wrapper, before the SDK's own SERVER span starts, with first request as the universal trigger (Express and Hono have no startup-completion event). The design.md §4 first-request guarantee is satisfiable only for spans the SDK produces: a SERVER span that user-run instrumentation starts before the wrapper runs precedes activation on the first request and falls to the §5 drop rule (§2). Activation is fully synchronous — resource construction per §2 (`defaultResource()` + synchronous `envDetector` attributes + static Apitally attributes, verified promise-free at resources 2.9.0), provider construction, pattern binding, a synchronous filesystem probe of the spool directory, starting unref'd timers, emitting the startup event — so the single-threaded event loop provides the concurrent-first-request guarantee without locks. Frameworks with real lifecycle hooks (Fastify `onReady`, Hapi `onPostStart`, NestJS/Adonis lifecycle) use those as the trigger in their adapters.

Test-environment detection at the activation boundary: `JEST_WORKER_ID`, `VITEST`, `NODE_ENV=test`, `APITALLY_DISABLED`, and the `disabled` option all skip activation permanently. Activation is attempted at most once per process; a failure logs at error level and the app serves untelemetered.

**Per-request context isolation**: each request runs under a fresh context (`ROOT_CONTEXT` base) established by the outermost wrapper, except when adopting a user instrumentation's SERVER span, in which case the SDK runs inside the user's context by design.

**Graceful shutdown** is layered, without ever installing termination-signal handlers:

- Express: the middleware ensures a `close` listener on the live server (`req.socket.server`, tracked per distinct server), covering `app.listen` and `http(s).createServer(app)` startups alike; when `app.handle` is invoked without a live server (serverless-style direct dispatch), the attach no-ops. Server close triggers a flush-and-send cycle, not teardown: the pipeline keeps running (all timers are unref'd, so it never holds the process open), an app dual-bound to multiple servers keeps full telemetry on the still-open one, and another server's in-flight requests are never discarded. Teardown belongs to `shutdown()` and the `beforeExit` floor.
- Frameworks with shutdown hooks (Fastify `onClose`, Hapi `onPreStop`, NestJS/Adonis lifecycle) wire those in their adapters.
- `process.on("beforeExit")` is the floor for clean exits; all SDK timers are unref'd so the SDK never keeps the event loop alive.
- A public async `shutdown()` at the package root is the documented path for Hono and custom lifecycles that never close the server.

None of these fire on a SIGTERM left to the default handler — the process dies before `close` or `beforeExit` — so the stock Kubernetes shutdown path drains nothing unless the app wires graceful shutdown (`server.close()` on SIGTERM, standard practice) or awaits `shutdown()`. The README and migration guide state this loudly; the worst-case loss without it is the last export interval (~15s) plus in-flight requests.

**Fork safety** is not a JS concern: `cluster` workers are separate processes that each configure and activate independently; there is no post-activation fork.

**Dual-build state**: tsup ships ESM and CJS builds, and a mixed-module app can load both copies in one process (each `import`/`require` site resolves its own exports condition). The SDK's process-global state — the config/activation singleton — therefore lives in a `Symbol.for`-keyed `globalThis` slot rather than module scope, so whichever copy activated, the other copy's `useApitally`, helpers, and `shutdown()` resolve the same instance. Context holders already cross copies: OTel's `createContextKey` is `Symbol.for`-based by design, and the context manager is shared through OTel's global API registry (one api instance guaranteed by the peer-dependency policy — §16). The slot guards every side effect, not just config: the framework wraps (`app.handle`, `app.fetch`) and the log patches (console, winston, pino) are check-and-mark operations against `Symbol.for`-keyed markers on the wrapped object, so a mixed-module app calling `useApitally` through both copies wraps and patches exactly once — no double SERVER spans, no double log capture (provider, context-manager, and propagator registrations are already once-only through the API registry's refusal). The slot also records the SDK version that populated it; a second copy at a different version warns once about the skew.

## 5. Request model: span filtering and exclusion

As `design.md` §5: the in-flight request map keyed by SERVER span id is the single keep/drop point, classification happens at span start, children inherit their local parent's entry, lookup miss defaults to dropped. OPTIONS, websocket schemes, and path/user-agent exclusions apply at the same point; path and query are derived from the full-URL attribute and written onto the span when the producing instrumentation omitted them. The per-message span drop (kind + name suffix + scope) is retained for user-owned socket instrumentations even though the SDK's own middleware never emits such spans.

## 6. Sampling and per-request buffering

Two-stage sampling, deterministic by trace ID, per `design.md` §6: the low 64 bits of the trace id (BigInt from hex) tested against `round(rate * 2^64)`; both stages test the same value so the overall probability is the minimum of the two rates. Callbacks receive the SERVER span and return `number | boolean | undefined` (`undefined` = abstain), and are synchronous — the request-stage decision runs inside span start, so a returned Promise counts as an invalid return; a throwing or invalid-returning callback warns and resolves to keep. Per-request buffers cap at 1,000 spans and 1,000 log records. Global bounds carry the reference's model: the payload stash is capped at 2,048 requests process-wide, oldest evicted with a debug log; span and log buffers stay per-request-bounded only, so a long-lived streamed connection (SSE, long-polling — websockets are excluded at §5) buffers its descendants and logs until the stream completes, exactly as in the reference implementation. A global in-flight budget would be a cross-SDK change to `design.md` §6, deliberately not introduced as a JS-only deviation.

**D2 — one unconditional release condition replaces the deferred-export commit protocol.** The reference implementation's `defer_export`/`finish_export` handshake (the transport commits at response start, with a cancel path when completion precedes span end) is not ported. The processor holds each request until both conditions hold; a span that ends before transport completion is held ended — deferral by another name, though with `instrumentation-http` span end (response `close`) normally follows transport completion (`finish`), making span end the usual trigger; the hold-after-end case belongs to abort races and producers that end before the response has streamed out — and the condition is unconditional and symmetric, so the commit/cancel choreography and the ad-hoc late-attribute merge disappear:

- The transport middleware accumulates everything it learns into one **per-request record**: status, sizes, final route, captured header/body payloads, timing.
- **One release condition for every request: transport completion AND SERVER-span end — whichever completes second triggers the release, exactly once per request** (shutdown's release of transport-complete requests goes through the same one-shot). Transport completion (response fully sent, streamed body fully consumed) finalizes the per-request record: the response-stage sampling decision runs and metrics are recorded at that moment, independent of span-end timing.
- **Release is an enqueue, not a processing step**: on keep, the buffered descendants, the SERVER span, and the request's logs are handed to the downstream batch processors, with the record and the payload stash attached to a private span copy (user-attached processors receive the original snapshot untouched). Export-copy construction, record application, masking, parsing, and redaction run in the exporter at batch-drain time — design.md §7's "processed outside request handling" reads, in a single-threaded runtime, as timer-driven exporter turns, never synchronously inside a request's dispatch (release on the owned path fires inside the `res.end` patch).
- Attribute writes during the request go through one write-through helper: write to the live span if recording, always mirror into the request record; the exporter applies the record onto the export copy last, so a record value wins over anything the producing instrumentation set for the same key (the SDK is route authority per design.md §8, and the record holds the final transport-observed values — the same precedence as the reference's `finish_export` merge).
- Exception events are not part of the record: every SDK event write (Express error middleware, Hono `errorHandler` wrap, `captureException`) lands while the span is still recording on both paths — adopted spans end on `close`, after the SDK's `finish`-time work — so spec §6.4's last-exception-wins ordering is plain append order. A `captureException` from async work that outlives the request is dropped, as in the reference and stock OTel.
- Spans the SDK created are ended at transport completion, so both release conditions coincide — the only owned-vs-adopted difference is that single `span.end()` call. Adopted spans end on their producing instrumentation's schedule (`instrumentation-http` ends on response `close`, which fires after `finish`), sit in the per-request buffer, and receive late attributes on the export copy.

What the record buys over the reference's held-span-plus-merge: metrics and response-stage sampling read from the record, span-independent — complete even when the user's sampler left the request's SERVER span non-recording — no span is adopted then, the record still carries metrics (§2 relies on this) — and the transport gets one accumulation point instead of scattered locals feeding a merge call. The cost, stated plainly: request attribute state lives in three places (live span, record, export copy). Trade-off, accepted: attributes that only reach the export copy are invisible to user-owned exporters on adopted spans — concretely, a streamed response under user-run `instrumentation-http` gets its final `http.response.body.size` and corrected route only on Apitally's copy; the user's own backend sees that span without them. The write-through helper makes this rare, and `design.md` only requires invisibility in the other direction (payloads).

Shutdown semantics: processor shutdown releases buffered requests whose transport already completed; buffers of still-in-flight requests are discarded, per `design.md` §6.

## 7. Capture pipeline

Follows `design.md` §7 with these JS mechanics:

- Capture decisions are header-only: content-type allowlist first, then the 50,000-byte cap with the `[BODY_TOO_LARGE]` sentinel; complete bodies only; a partial buffer from an aborted stream is suppressed.
- Express request bodies are captured with a passive `req.emit` wrap on the `IncomingMessage`, observing `data`/`end`/`aborted` events as they pass through — the stream's flow state is only ever changed by the app's own consumer (body-parser included), never by the SDK, with a running length check per observed chunk (the async message-based transport rule). A body no consumer ever reads is not captured.
- Hono request bodies are captured passively too, through Hono's body cache — by inspecting `c.req.bodyCache` (a plain field) at transport completion, never by calling the request's body methods: a byte-faithful cache entry (`arrayBuffer`, `text`, or `blob`; `c.req.json()` reads through `text`) is awaited with rejection handling (a poisoned entry means no capture) and its bytes captured. `parsedBody`/`formData` entries are not captured — re-serializing them would fabricate bytes that never crossed the wire (fresh multipart boundaries, re-ordered fields). An empty cache means no capture and no read: calling a body method there would consume the stream and cache a rejected promise onto the app (Hono caches whatever `raw[key]()` returns — verified at 4.11). The SDK never writes to the cache and never reads the request stream. An unconsumed body is not captured (v0 read it after the response; dropped — a post-response network read can stall on an unfinished client and needs its own cap-aware stream reader), and a body consumed directly off `c.req.raw` bypasses the cache and is not captured. Both adapters share one contract: a body the app never reads is not captured.
- Response bodies: Express via `res.write`/`res.end` patches; Hono via the ported v0 `captureResponse` stream-teeing helper (including its Bun workaround). Capture position is pinned wire-side on both adapters: the Express patches are installed in the `app.handle` wrap before the middleware stack runs, so a compression middleware's output feeds the SDK's patch, and the Hono tee wraps the Response the app returned, after any compress middleware — the SDK always observes the bytes that cross the wire. The 50,000-byte cap and the body size attributes measure those same wire bytes (what Content-Length describes), so the header short-circuit and running-count paths agree by construction; a compressed body follows the bytes path below (parse attempt fails, gzip pass-through) with the captured Content-Encoding header saying what it holds, and mask callbacks receive the wire bytes — compressed when the response was compressed.
- **Payload isolation**: the write-through helper (§6) has exactly two data classes — regular attributes (live write + record mirror) and capture payloads (header maps, body bytes), which are stash-only, never touch the live span, and are masked/redacted/attached only to Apitally's export copy, in the exporter at batch-drain time (§6), off the request path. A span that fails redaction is dropped, never exported raw.
- Mask callbacks: `maskRequestBody(body: Buffer, span)` returning `Buffer | null`; returning nothing, throwing, or returning the wrong type (a Promise included — mask callbacks are synchronous) yields `[REDACTED]`. A throwing or wrong-type-returning callback additionally warns once per process per callback — fail-closed with no signal is the classic "every body shows `[REDACTED]` and nothing explains why" support ticket (§12: users must be able to tell when something is broken); a `null`/`undefined` return is the documented redact-everything signal and stays silent. Documented contract: may run later, off the request path, against an ended span snapshot.
- Body processing order (mask → parse → redact → serialize), JSON detection by parse attempt, bytes-valued attributes for non-UTF-8 bodies, gzip pass-through for pre-compressed response bodies, header redaction (list-valued single `[REDACTED]`, `Location`/`Content-Location` query redaction), and the export-boundary query/header redaction pass over both semconv normalizations all follow `design.md` §7.
- Body size attributes are set independently of capture toggles: Content-Length when trustworthy, else a running byte count finalized at transport completion; unknown size skips both the attribute and the histogram observation.

## 8. Transport observation, routes, frameworks

**D3 — SDK-owned middleware produces the SERVER span.** In JS, "stock instrumentation" for the SERVER span means module-loading interception (`instrumentation-http` patches `node:http` at require time; `instrumentation-express` only decorates). That path's documented setup requires init-before-imports or `--import` loader flags, and Bun lacks the ESM loader hooks entirely (`module.register` unimplemented) — both incompatible with one-line setup on this SDK's platform scope. (A late-enablement trick exists — the patch mutates `http.Server.prototype.emit` in place, and require-in-the-middle also patches `process.getBuiltinModule`, so a forced builtin re-require after enable activates SERVER spans even on Bun — and is rejected: it rides undocumented require-in-the-middle internals, degrades silently to zero spans without the forced trigger, and still produces route-less generic-named spans, because `instrumentation-express`, the `http.route` source, emits INTERNAL-only spans and stays inert under init-after-imports on ESM and Bun — the SDK's middleware would have to exist anyway.) The JS ecosystem's own framework instrumentations (`@hono/otel`, `@fastify/otel`) are middleware/plugin based; this SDK follows that pattern for every framework: the transport middleware is also the span producer, emitting stable semconv, extracting W3C `traceparent`, and starting the span as a local root under a fresh context. The middleware sets HTTP RPC metadata on that context (`setRPCMetadata`, exactly as `instrumentation-http` does) — the ecosystem's "a transport span exists" beacon: `@fastify/otel` >= 0.19 demotes its request span to INTERNAL on this signal (earlier versions never emitted SERVER spans), so middleware-based producers that honor it coexist without duplicates.

**Adoption**: when the outermost wrapper finds an active, recording SERVER span (the user runs `instrumentation-http` or equivalent through their own setup), the SDK adopts it — no second SERVER span — and layers the per-request record, capture, and metrics on top. With instrumentations registered but no user provider, the OTel proxy delegates to Apitally's provider from activation onward, so user-registered contrib instrumentations (DB clients, HTTP clients) feed descendants into Apitally with zero per-library SDK code. Instrumentations bound to an explicit non-global provider route past the SDK: documented limitation, as in the reference. Middleware-based producers that ignore RPC metadata (`@hono/otel` today) start their SERVER span inside the framework chain, after adoption has decided; the span processor detects the nested SERVER span under an in-flight request, binds it to the same request entry, demotes it to INTERNAL on Apitally's export copy (Apitally never double-counts — including when a previously dormant middleware wakes up because the SDK registered the global provider), and warns once naming the producing scope. The duplicate in the user's own exporters is theirs to resolve by removing the producing middleware; the warning says so.

Outermost observation per phase-1 framework:

- **Express**: `useApitally` wraps `app.handle` — the single entry point for every request, position-independent for span production, covering 404/`finalhandler` and error-handler responses. Response observation via `res.write`/`res.end` patches plus `finish`/`close` listeners. A lazily-appended error middleware (first request) captures the error object for the exception event. Route templates come from **registration-time capture** — the mechanism every major agent converged on (dd-trace, New Relic, Elastic, OTel `instrumentation-express`), because router 2.x (all of Express 5) keeps the template only inside a path-to-regexp closure, statically unrecoverable after registration (pillarjs/router#122). Those agents load before all user code via `--require`/`--import`; this SDK rejects loader flags (D3), so it ships the load-first substitute as a public side-effect entry: **`apitally/express/register`, imported on the first line of the entry module, is the documented Express setup for every app shape — one rule, no per-shape forks.** The register entry peer-resolves express via `createRequire`, finds the shared router prototype through a probe router (the same find-the-owner walk that absorbs the Express 4/5 structural difference), and installs the capture patch before any user module registers a route — module-scope routers included, the layout import hoisting otherwise breaks; captured path arguments buffer config-free per router instance in a WeakMap. `useApitally(app)`, placed anywhere after app creation, reads that WeakMap and assembles the full template per request with mount-stack semantics modeled on `instrumentation-express` (segment push/pop on `next()`, Express 5 wildcard filtering, final prefix-match validation). The patch is check-and-mark (§4) and `useApitally` also installs it through the app's own prototype, so registrations after `useApitally` are captured even without the register import — and that same pass is the safety net for a bundled or duplicated express copy the peer resolution cannot see (the D4 limitation class). A request routed through a registration the SDK never saw fails route validation and exports a cleared route (`design.md` §8 semantics), loud and actionable at two points: mounting a router that has layers but no capture record warns once naming the fix (the missing first-line register import), and the per-request cleared-route path warns once naming the consequence — empty-route requests are skipped by the request histograms (spec §7.1), surviving only as request logs. v0's response-time reconstruction is not ported on either major — it read Express-4-only layer internals and, on 5, mutable post-dispatch layer state. Express 4 inline-regex params are normalized in captured templates; Express 5 rejects them at registration.
- **Hono**: `useApitally` wraps `app.fetch` (span, fresh context, response observation — `onError`-synthesized responses return through it) and registers a thin inner middleware that records the matched route onto the per-request record after `next()` — template and match state read via the supported `hono/route` helpers (`c.req.routePath` is deprecated at 4.11; real handlers are discriminated from middleware entries by handler arity, per Hono's own convention). Hono composes handlers in registration order and a route handler returns without calling `next()` (verified at 4.11.4), so the inner middleware only runs for routes registered after it — which sets the ordering contract below. The `onError` handler is wrapped through the runtime-accessible `errorHandler` property (duck-typed, defensively) to record the exception event — lazily on the first request, not at setup: `route()` mounting identity-compares a sub-app's `errorHandler` against Hono's module-level default to pick its composition path (verified at 4.11), and a user's own `onError` may legitimately be registered after `useApitally`; first-request wrapping sits after both. A handler replaced after the first request loses exception capture — accepted edge. Instrument the root app, not sub-apps mounted into another app (documented). 404-ness is derived from route-match state plus the response status, since Hono holds its `notFound` handler in an ES private field that cannot be read or composed. Works identically on Node (`@hono/node-server`) and Bun. Setup contract, documented loudly in README and migration guide alongside the Express ordering rule: **`useApitally` runs immediately after the app is created — before middleware and route registrations (v0's documented placement; idiomatic for every Hono middleware) — and before `app.fetch` is handed to the server.** The registration half is softer than Express's rule: `app.route()` re-registers a sub-app's routes on the parent at mount time, so module-scope sub-app assembly is harmless as long as the mount call follows `useApitally`. Violations are loud and immediate: `app.routes` is typed public, so `useApitally` on an app with existing registrations warns once at setup naming the consequence (those routes export cleared and skip the histograms, spec §7.1) and the fix. The serve half has no probe: `serve({ fetch: app.fetch })`, `Bun.serve({ fetch: app.fetch })`, and `export default app` are the canonical serve idioms, not edge cases, and a reference grabbed before the wrap bypasses the SDK entirely (no spans, no metrics, and no warning possible — the wrap replaces the `fetch` property and a previously captured reference is unreachable).

Route authority per `design.md` §8: the SDK sets `http.route` to the parameterized template including mount prefixes, clears wrong routes on unmatched requests (exported with empty route; histograms skip them), and names spans `{method} {route}`. Version floors (Express >= 4, Hono >= 4, refined during implementation) are validated against context-propagation correctness, not API surface.

## 9. Logs

**D4 — capture surface via SDK-owned attachment-only patches, not contrib instrumentations.** The chosen surface is `console` + winston + pino (plus the NestJS logger with its adapter). The governing rule, PoC-verified at winston 3.19.0 and pino 10.2.0: patches only *attach*; log data flows exclusively through each library's official extension contract, downstream of the application's own logging policy — so pino `redact` paths and serializers, winston `silent`, level thresholds, and logger-level formats (redacting or dropping) all apply before the SDK sees a record, and the SDK never exports data the user's logging config strips. If library internals drift, an attachment-only patch degrades to capture-not-attached (loud in tests and the version matrix), never to capturing unredacted data.
- **console**: global method wraps ported from v0 — console has no policy layer to respect; the wrap is the seam.
- **winston**: an `ApitallyTransport` (subclass of the winston-transport base resolved alongside the peer; marker-keyed, no level, no transport format) receives records through the official transport contract. The only patch is a `Logger.prototype.write` shadow — the shared prototype found by walking a probe logger's chain to the owner of `configure`, since `createLogger` mints a per-call `DerivedLogger` subclass — that never reads the info argument: it only ensures the transport is attached via the official `logger.add()` (re-attaching after `clear()`) and delegates. Known behavior: winston buffers entries on zero-transport loggers, so the first attach drains that backlog into the transport — those records were never delivered anywhere, capturing them is honest. Verified from winston 3.2.0 (where `Logger.child` arrived) through 3.19.0 with zero mechanism drift; peer range `>=3.2.0 <4` (spike 8).
- **pino**: the write-method patch (keyed by `pino.symbols.writeSym`, on the prototype that owns it, found by walking a probe instance's chain from the peer-resolved copy — the owner is a grand-prototype shared by every logger and child of that copy) is demoted to a discovery point that never reads the log object: per call it ensures the official `hooks.streamWrite` hook is installed on the resolved hooks object (composing after any user hook) and stashes the numeric level argument for the strictly synchronous hook call that follows, then delegates. Capture reads the post-redaction, post-serializer line from the hook — message parsed at the logger's configured messageKey, severity from the stashed level number (immune to `formatters.level` rewrites). Loggers created without a `hooks` option share pino's module-level default hooks object, so one installation covers all of them, pre-existing and future; worker-thread transports are covered because the hook runs on the main thread before the transport handoff, and multistream captures exactly once. `hooks.streamWrite` sets the pino peer floor: it landed in pino 9.6.0 (no 8.x release has it), so the peer range is `>=9.6.0 <11`; below the floor the patch degrades to silent no-capture — the hook installs but never fires — which the docs state plainly (spike 8).

All captured records emit into the private `LoggerProvider` through `api-logs` (severity mapping per spec §8, instrumentation scope name = logger name, `console` for console). Rationale: the contrib logging instrumentations are require-hook based (a logger created at module scope before `useApitally` is never captured) and the winston bridge hard-codes the global logger provider, conflicting with the private-provider invariant. Users who run the contrib logging instrumentations anyway coexist without duplication: their instrumentation emits into the global logger provider, the SDK's patches into the private one — disjoint destinations, each log delivered once to each backend (captured bodies may carry the contrib-injected `trace_id`/`span_id` correlation fields). winston and pino are optional `peerDependencies` so the SDK patches the user's copy under strict package layouts (pnpm). Known limitations, documented: loggers created inside worker threads and per-instance write overrides evade the prototype-level attach points (worker-thread transports do not — the pino `streamWrite` hook runs on the main thread before the transport handoff); bundled server code that inlined its own winston/pino copy (esbuild/tsup/Next.js server bundles) and multi-copy installs escape the peer-resolved attach.

Request linkage, the drop rule, SDK/OTel self-log exclusion, per-request buffering, and the 2,048-character truncation follow `design.md` §9 — the exclusion is structural in JS: the internal logger writes to stderr, bypassing the patched console (§12), OTel diag is silent by default and the SDK never installs a console-backed diag logger, and records emitted outside any request fall to the drop rule as a second layer. **D7 — platform gap, recorded**: `code.file.path`/`code.line.number`/`code.function.name` are omitted — JS logging libraries do not carry caller location without expensive stack capture.

Startup event per spec §9: scope `apitally`, event name `apitally.app.startup` in the native `eventName` field (fully supported at the pinned versions — carried through the SDK and landing in the proto `event_name` field, structured body intact; no attribute fallback — spike 4), JSON body with `framework` (`express`, `hono`), `versions` (`node`, framework, `app` when `appVersion` set), lazily-enumerated `paths` (Express: from §8's registration-capture table). `openapi` is omitted for the phase-1 frameworks; framework-native spec sources (e.g. Hono zod-openapi) are a later refinement.

## 10. Export pipeline

As `design.md` §10, with these JS bindings:

- **Intake**: stock `BatchSpanProcessor` and `BatchLogRecordProcessor` with every parameter passed explicitly (~1s schedule delay) — constructor config beats `OTEL_BSP_*`/`OTEL_BLRP_*` env vars for every parameter (spike 2), provided the values are concrete: explicit `undefined` counts as omitted and lets env in, the span-processor shim mutates the config object it receives (each processor gets a fresh literal), and `BatchLogRecordProcessor` takes a single options object — the old positional `(exporter, config)` form constructs a silently broken processor.
- **Encoding**: `@opentelemetry/otlp-transformer` protobuf serializers (`ProtobufTraceSerializer`, `ProtobufMetricsSerializer`, `ProtobufLogsSerializer`) — no stock OTLP exporter in the path. The content-hash dedup contract rides on replaying stored spool bytes (`design.md` §10: serialize once, compress once), not on serializer determinism; the serialization details the export path does depend on are verified (spike 3): `Buffer`/`Uint8Array` attribute values serialize to `bytesValue` through the writer's runtime type check, and export copies must share `resource`/`instrumentationScope` object references across a batch — the serializer groups by identity, so per-span clones fragment `resourceSpans` and bloat payloads.
- **Spool**: v0 `TempGzipFile` mechanics (node:zlib gzip streams into `os.tmpdir()`, recognizable `apitally-*.gz` naming) carrying the full `design.md` semantics: per-signal files, 4 MB uncompressed rotation checked before append, appends in bounded sub-chunks (the reference's 32-record count chunks — a count is not a byte bound, so an append of pathologically large records can overshoot the file threshold; accepted, because the server's payload caps hold with wide gzip margin for everything short of deliberate multi-MB span attributes), 50 MB disk / 10 MB memory caps with metrics-last eviction, 59-minute retention after first send attempt, 2-hour orphan cleanup, per-cycle mtime touch, synchronous writability probe with in-memory fallback. One JS refinement on the design.md mechanics:
  - **Serialized spool operations.** gzip and file streams complete across event-loop turns, so append, rotate, close, upload-eligibility, deletion, and shutdown drain are serialized on one per-signal operation queue: every append resolves against a specific file generation, a file becomes uploadable only after both its gzip and file streams have closed successfully, a stream error invalidates the current generation (discard with deduplicated warning, per design.md §10), and the final drain awaits the queue before closing and sending.
- **Worker**: one unref'd-timer worker; 15s interval ±10% jitter, first export ~2s, 10 files per cycle oldest-first, 0.1-0.5s inter-send pauses, 10s POST timeout (`AbortSignal.timeout`), `Apitally-Export-Interval` response header clamped to [5, 60], retryable = connection errors/timeouts/408/429/5xx with one immediate inline re-POST on connection error; a retryable failure ends the cycle with the file left queued — design.md's "one probe POST per cycle during an outage" is this stop-on-failure rule, not a separate mechanism (reference parity) — while permanent 4xx drops the file with a once-per-status warning and the cycle continues. Cycles are serialized on one timer chain — the next cycle is armed only after the current one completes, the interval measured from cycle end, so an overrunning cycle (worst case against a dead endpoint: 10 files x 10s timeouts is minutes, not seconds) stretches the cadence instead of stacking; a flush request (server close, `shutdown()`) arriving mid-cycle awaits the running cycle rather than starting a second. Under sustained overload the loss posture is the spool's: size caps evict oldest closed files metrics-last, attempted files expire after 59 minutes — loss is bounded and oldest-first. Cycles run under `suppressTracing`, honored end-to-end at current versions including `instrumentation-undici` (the historical 0.19.0-era gap is closed at 0.30.0 with sdk-trace 2.9 — spike 6); the SDK's own undici instrumentation instance additionally gets an `ignoreRequestHook` matching the Apitally endpoint — the hook is this instrumentation's explicit contract and stays the primary mechanism. On adopted setups where the user runs their own undici instrumentation, export POSTs are suppressed via `suppressTracing` on current versions; instrumentation copies predating the fix ignore it and produce CLIENT spans into the user's exporters — documented limitation. Final drain on shutdown: uncapped, unpaced.
- **HTTP client**: global `fetch`. Proxy support per the standard env vars, resolved once at activation (§16 — nothing resolves at module scope): on Node, undici's `EnvHttpProxyAgent` passed as the per-request `dispatcher` (constructed only when proxy vars are present — it is experimental in undici 6 and warns on construction, and the user's global fetch is never touched); on Bun, the native `proxy` fetch option. undici is a regular dependency, pinned `^6` (§16 — newer majors raise the Node floor above §1's).
- Headers: `Authorization: Bearer`, `Apitally-Env`, `Content-Type: application/x-protobuf`, and `Content-Encoding: gzip` per spec §2-§4, plus `User-Agent: apitally-js/<version>`.
- **Metrics collection is worker-driven**: a non-periodic `MetricReader` subclass; the worker calls `collect()` each cycle so all three signals export together.

## 11. Metrics

Three request histograms under scope `apitally`, exponential buckets, delta temporality — aggregation type and temporality configured through the SDK's non-periodic reader's selector options so the overrides apply to histogram instruments only (selector options are honored on `MetricReader` subclasses; `PeriodicExportingMetricReader` would ignore them and consult only the exporter's `selectAggregation`/`selectAggregationTemporality` methods — spike 5). JS `sdk-metrics` exposes no scale configuration (the aggregator starts high and only rescales down as the data range demands) while the ingest endpoint accepts scales in [-2, 6] and drops data points outside, so the export path downscales exponential histogram data points to scale <= 3 (bucket-merge by powers of two) before serialization — matching the reference implementation's `max_scale=3`. The merge is exact, not lossy relative to the reference: exponential buckets nest by powers of two, so scale-3 output built by merging equals what a native scale-3 aggregator records — verified bucket-for-bucket on real data points, `Math.floor(oldIndex / 2**(srcScale - 3))` with count/sum/min/max/zeroCount passing through (spike 5). Recorded at transport completion from the per-request record (§6), independent of span-end timing and sampling; excluded and sampled-out requests counted; OPTIONS, websocket, and unmatched-route requests skipped. Data point attributes per spec §7.1 plus `url.scheme` and `error.type` (status as string, 5xx only).

**D5 — process gauges implemented in-SDK.** `process.cpu.utilization` (cpuUsage delta normalized across CPUs), `process.memory.usage` (RSS), and `process.uptime` are three observable gauges on the private MeterProvider, ported from v0 `resources.ts`, observed in the worker's collection cycle (which yields the spec's timestamp pairing). Rationale for deviating from the community-package guidance: `@opentelemetry/host-metrics` is deprecated in favor of `@opentelemetry/instrumentation-host-metrics`; both accept a private MeterProvider and scope down to process-only instruments via `metricGroups`, but neither emits `process.uptime`, and the successor is a fresh 0.x version line — a new deliberately-pinned dependency that covers two of the three gauges is a worse trade than the ~40 ported lines.

## 12. Error handling and logging posture

Per `design.md` §12: every entry point wraps in try/catch, the SDK never breaks the app, warnings are reserved for actionable data loss, enrichment failures log at debug, repeated warnings deduplicate, the write token never appears unmasked in logs. In JS that rule has an async half: an unhandled promise rejection crashes a Node process, so every SDK-created promise chain — timer callbacks, event listeners, fire-and-forget sends — carries rejection handling. Internal SDK diagnostics go through a minimal internal logger (~20 lines) that writes directly to `process.stderr`, never through `console` — the console methods are a capture surface (§9), so routing SDK output around them makes self-capture structurally impossible: no marker or exclusion logic, and export-failure warnings cannot feed back into the export path. Warnings and errors always emit — users must be able to tell when something is broken — while debug output is gated on `APITALLY_DEBUG`.

## 13. Public API

Root entry (`apitally`):

- `useApitally(app, options)` — synchronous; duck-type framework detection (the v0 name kept: JS named imports strip the package namespace, so a bare `init` would say nothing at the call site — `design.md` §13's "each language's idiom" clause) (Express: function with `use`/`handle`; Hono: object with `routes`/`fetch`/`route`; extended per adapter phase); delegates to the matching adapter; a detection failure throws an error naming the framework subpath entry point. Adapters carry zero runtime framework imports (type-only), so the root entry stays small and side-effect-free.
- `setConsumer(identifier, { name?, group? })`, `setRequestAttribute(key, value)`, `captureException(error)` (`error` is `unknown` — JS code throws non-Error values; OTel's `recordException` coercion applies) — resolved through the request-scoped span handle; no request/context argument. The handle is a holder installed into the OTel context by the transport middleware and filled by the span processor at SERVER-span start (filled directly by the middleware on the adoption path). The consumer holder additionally lets middleware outside the SDK's layers set a consumer that the processor writes onto the span at start; the consumer dimension survives sampling into metrics.
- `shutdown()` — async final drain (§4), idempotent.
- `instrument(fn)` / `instrument(name, fn)` and `span(name, fn)` — manual tracing: INTERNAL child spans under tracer scope `apitally.otel`; `instrument` sets `code.function.name` from `fn.name` and file/line captured once at wrap time. Wrapped functions may be sync or async: a returned promise passes through and the span ends when it settles, recording a rejection as the exception; a sync throw ends the span the same way.

Per-framework subpaths (`apitally/express`, `apitally/hono`, ...) export exactly the framework-typed `useApitally` (plus its option types) — nothing else; any future framework-specific helper is a deliberate API addition, not an open-ended promise. Express additionally ships the side-effect entry `apitally/express/register` (§8): no exports, imported for its import-position-significant effect. The root entry also exports `ApitallySpanProcessor` for attachment to existing OTel setups (the D1 path).

**D6 — instrumentation helper wrappers are omitted.** `registerInstrumentations([...])` is already the JS one-liner (`design.md` §13 explicitly skips wrappers in that case); cooperation with user-registered instrumentations comes from the provider mechanisms in §8. `instrumentation-undici` is the one instrumentation the SDK enables itself at activation, and only when the SDK constructed its own tracer provider — on adopted setups the user's instrumentation set owns client-span production (`getNodeAutoInstrumentations` already includes undici; a second instance would emit duplicate CLIENT spans into the user's exporters). (diagnostics_channel based — no module hooks; the SDK's instance gets an `ignoreRequestHook` for the Apitally endpoint — §10; Bun's native fetch does not emit its events — documented gap.) A `--import` auto-instrumentation entry point is out of scope for 1.0 (demand-driven roadmap item).

0.x removals per `design.md` §13, plus JS-specific ones: `clientId` → `writeToken`; the hub client, request/error counters, and NDJSON request logger → OTel pipelines; `excludeCallback` → sampling callbacks; per-framework `setConsumer(req, ...)` and the `req.apitallyConsumer` / context-variable patterns → the root `setConsumer`.

## 14. Sentry integration

Auto-detect at activation, public API first with a carrier fallback (spike 7). Primary: `getClient()` off a synchronous `createRequire("@sentry/node")` peer resolution (the same mechanism as every other optional peer, §16, so activation stays synchronous; no import of `@sentry/node` at module scope — the package is a types-only optional peer). That resolves wherever `@sentry/node` is reachable — as a direct dependency, or as the transitive dependency every wrapper package (`@sentry/nextjs`, `@sentry/bun`, `@sentry/aws-serverless`) hoists on npm-style layouts — and returns the same client instance the wrapper initialized (the client lives on the global carrier, so dual-copy concerns are moot; verified). Fallback, for strict layouts (pnpm, Yarn PnP) where transitive deps are not resolvable from the app: the `globalThis.__SENTRY__` carrier walk, which has exactly two shapes across the supported majors — v7 `__SENTRY__.hub.getClient()`; v8-10 `__SENTRY__[__SENTRY__.version].acs.getCurrentScope().getClient()` (byte-for-byte what public `getClient()` does). With a client present, subscribe `client.on("beforeSendEvent", ...)` — available and firing with `event.event_id` on every verified package and major, v7 included; for exception events, write `event.event_id` onto the active SERVER span as `apitally.exception.sentry_event_id` through the span handle. Failures log at debug. Supported set: `@sentry/node` >= 7 plus `@sentry/nextjs`, `@sentry/bun`, `@sentry/aws-serverless`; no Sentry package ships ESM-only; the matrix pins Sentry majors 7 and 10.

## 15. Cross-language posture

Shared invariants per `design.md` §15 with `telemetry.distro.name` = `apitally-js`. JS idiom: camelCase options, `Buffer` for body bytes, promises for the async lifecycle surface (`shutdown()`) while user callbacks (sampling, masking) stay synchronous by contract, `AsyncLocalStorage` as the execution-context primitive, unref'd timers as the background primitive (the JS reading of "thread" — total background machinery: two batch processors plus one export worker timer).

## 16. Code style and testing

Carried in this repo's AGENTS.md (authored in phase 0 from `design.md` §16, modeled on the Python AGENTS.md). JS-specific rules recorded here:

- Node >= 20.6 syntax; TypeScript strict, ES2022, NodeNext resolution.
- Biome for linting and formatting; tsc for type checking; tsup (unbundled, dual ESM+CJS) for build; attw for package-shape checks.
- Never use `instanceof` across OTel package boundaries — duck-type on properties; the user's OTel objects may come from a different package copy.
- Optional peers (winston, pino — both CommonJS) are resolved with `node:module` `createRequire`, synchronously: activation is synchronous, so dynamic `import()` never sits on that path. Resolution happens at activation, never at module scope — module load stays side-effect-free. The `createRequire` anchor must survive both build formats: tsup rewrites `import.meta` to an empty object in CJS output, stranding `createRequire(import.meta.url)`, so the build sets tsup `shims: true` (which reconstructs `import.meta.url` from `__filename` in CJS) and built-artifact tests prove peer discovery through both the ESM and CJS entries. The Node-only undici proxy dispatcher follows the same rule: resolved at activation on Node when proxy env vars are present, so Bun never loads it.
- Dependency policy: `@opentelemetry/api` is a peerDependency (`^1.9.0`, plus a devDependency for tests) — the API's global registry refuses writes when two api copies differ in exact version (verified at 1.9.0), so a second copy in the user's tree could silently kill the SDK's provider/context-manager/propagator registration; a peer guarantees the one shared instance the dual-build argument (§4) also rides on. OTel stable SDK packages (`^2.9.0`) as regular dependencies, undici pinned to `^6` (undici 7 declares engines `>=20.18.1` and undici 8 `>=22.19.0`, both above the §1 floor; the 6.x line remains actively maintained and carries `EnvHttpProxyAgent`; Renovate never crosses this major — revisited when the §1 floor moves); experimental OTel packages (`sdk-logs`, `api-logs`, `otlp-transformer`) pinned per-minor (`^0.220.0`) and `instrumentation-undici` (contrib repo, own version line) pinned per-minor (`^0.30.0`), all bumped deliberately via Renovate with CI proof; frameworks and log libraries as optional peers (winston `>=3.2.0 <4`, pino `>=9.6.0 <11` — the spike-8 floors); `sideEffects` is an array naming only the `./express/register` entry files (so bundlers keep the bare import) — everything else happens inside `useApitally`.
- Testing per `design.md` §16: vitest; in-memory exporters/readers for shared modules; framework test clients driving small uniform real apps; a scriptable stub OTLP server only where the export transport is under test; a global setup that isolates OTel globals, the config singleton, env vars, and patches between tests (teardown-based resets — tests never pre-clean); a Bun smoke suite (`bun test`) covering the Hono integration on Bun. Test seams are mutable objects (replaceable factory properties): ESM module namespaces are immutable and `bun test` has no vitest-style module mocking, so Python-style module monkey-patching does not port.
- Test conventions: two-tier layout (`tests/shared/<module>.test.ts` mirroring source modules; per-framework integration dirs with a uniform app fixture); subject-predicate naming (`describe` = module/adapter name, `it` = present-tense behavior predicate, no `should`), with shared scenarios using identical `it` strings and the same canonical order across framework files; files ordered core behavior → edge cases → failure paths → shutdown, hooks at top. Scenario selection is contract-derived — each test pins a spec MUST, a settled design decision, or a plausible regression (authority cited in the plan; the citations are build-time scaffolding for scenario-selection review at the two audit gates and die with the planning docs — what survives in the repo is each test's subject-predicate name stating the contract in plain language), and fails only when user-observable behavior regresses: documented gaps, internal mechanisms, and constants are never pinned — with the Python suite mined as evidence, not authority. No wall-clock sleeps or fake timers: deterministic seams only (callable worker cycle, injectable pauses and timeouts, force-flush reads, provider force-flush ahead of assembly assertions, mtime manipulation, child-process exit for event-loop liveness). Assertions are exact-by-default: exact counts, full attribute equality, protobuf-decoded payloads in export tests; no snapshots. Coverage ownership: every behavior is asserted in exactly one home — the lowest layer that can observe it; `tests/shared/` owns core semantics, framework suites own adapter behavior, wiring, and the canonical cross-framework set (the only sanctioned duplication — scenarios whose integration failure while the module suites stay green would indicate an adapter or wiring defect); helpers stay consolidated — extend an existing helper over adding a sibling.

## Deviation summary

| # | Deviation | Rationale |
|---|---|---|
| D1 | Existing providers: instruct-only — warn once, the user adds the root-exported `ApitallySpanProcessor` to their setup; no provider-internals access anywhere | OTel JS 2.x removed `addSpanProcessor`; every alternative is private state, restructured across packages mid-2.x |
| D2 | One unconditional release condition (transport completion AND span end) + per-request record replace the deferred-export commit protocol | A span ending before transport completion is still held; what disappears is the commit/cancel handshake and ad-hoc late-attribute merging |
| D3 | SDK middleware produces the SERVER span; adopts user spans when present | Module-hook instrumentations break one-line setup and Bun; middleware is the JS ecosystem norm |
| D4 | Log capture via SDK-owned attachment-only patches (console wraps; winston ensure-attached transport; pino `streamWrite` hook retrofit) into the private LoggerProvider | Contrib logging instrumentations are require-hook based; winston bridge hard-codes the global provider; official data seams keep capture downstream of the app's own redaction and suppression |
| D5 | Process gauges implemented in-SDK (ported v0) | Community package (deprecated, mid-replacement) lacks `process.uptime`; a new 0.x dependency for two gauges is a worse trade |
| D6 | No instrumentation wrapper helpers; undici instrumentation only | `registerInstrumentations` is already a one-liner; everything else follows from provider cooperation |
| D7 | Code-location attributes omitted on log records | JS loggers lack cheap caller location |
| D8 | Adopted-span export copies get `deployment.environment.name` rewritten to the activation-resolved env when it differs (user span/resource untouched) | Spec §5 requires the key to match the `Apitally-Env` header; a user provider's resource is private state in OTel JS 2.x, unreadable at activation, so the header cannot follow it |
